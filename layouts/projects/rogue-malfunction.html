Project overview

A puzzle game where the controls work against you

Rogue Malfunction is an isometric puzzle adventure about a robot trying to escape its creator, the Overlord. In some levels, the Overlord changes the controls to make escaping harder.

The game has four puzzle rooms. Some change how movement works, while others focus on parkour, moving boxes, pressure plates, or finding a safe path through the room.

I came up with the control-remapping idea because I wanted the game jam theme, Going Rogue, to be part of the gameplay and not just the story.

Player controllers

Separating the controllers so we could work at the same time

We started with one player controller that all three programmers were going to use. That sounded fine at first, but each level needed different movement and balancing changes. Having three people changing the same script would have caused merge conflicts and slowed everyone down.

We made separate copies of the original controller for each programmer. That let us work on our levels without constantly touching the same file. It worked for the jam, but it also meant that we ended up with the same movement code in several scripts.

My control-remapping system

My Sequence level has three timed door puzzles. Each door gives the player a WASD sequence that has to be entered before the timer runs out.

Finishing the first door swaps W and S. Finishing the second swaps A and D. The player then reaches the last door with both changes active.

I built a control manager that keeps track of what each movement key currently does. The player controller checks that manager whenever it reads movement. I also built the door system that handles the sequence, timer, input feedback, failure state, control change, and exit.

Door 1Three inputs in three seconds
Door 2Six inputs in five seconds
Door 3Nine inputs in eight seconds

The remapping in the released game is set up by hand. It is not random. For Sequence, I changed the controller so it could read the current key mapping. It also uses smoothed movement, full air control, grounded jumping, wall anti-stick handling, and input locking while a door puzzle is open.

The four levels

Four different approaches to the same escape

The final build has four puzzle rooms. Ethan created The 3 B's, Phillip created Sokoban and Tiles, and I created Sequence.

Sequence uses timed door puzzles, control changes, parkour, moving obstacles, and falling hazards. The 3 B's uses movable objects, buttons, doors, and control inversions. Sokoban is built around moving boxes onto four pressure plates. Tiles asks the player to cross 25 tiles without stepping on one twice. If they do, the puzzle resets and sends them back to the checkpoint.

Robot character

Alice created and rigged the robot model after the jam. We had trouble getting the animations and player controller to work together. Rather than delay the release again, we used the robot as a non-playable character in the Sequence and Tiles scenes.

Playtesting

Making Sequence easier without removing the challenge

Playtesters kept telling me that Sequence was too difficult. I changed the parkour route three times and moved several of the jumping sections closer together.

I still wanted it to be the hardest level, so I added an Extremely Hard label to the level selection screen. Players knew what they were choosing before they entered, and I stopped getting complaints about the difficulty.

Playtesting also exposed progression bugs and edge cases that we fixed after the jam. During that time, I also built the pause menu, controls page, settings flow, updated menu navigation, and level selection screen.

Retrospective

What I would change now

Player-controller setup

Making separate controllers solved a problem during the jam, but I would not build the system that way again. We ended up with the same movement code in several scripts.

If I rebuilt it, I would keep one movement controller for physics, jumping, and interaction. The control-remapping system would be separate, and each level would tell it which control setup to use.

GitHub workflow

I would set up main, development, and feature branches from the beginning. I would also make it clear who owns each shared script, scene, and prefab so we are not all changing the same files.

Connecting the levels

Each programmer made their level mostly on their own, so the four levels feel separate. If I made the game again, I would plan the full level order and story first.

I would use the environments to show more about the robot, the Overlord, and why the robot is trying to escape.

Communicating difficulty

I also learned that difficulty needs to be communicated clearly. I kept Sequence hard, but the Extremely Hard label told players what they were choosing before they entered.
